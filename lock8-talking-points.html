The Case for Change

24Content & Editing Clients edit content, never structure — brand integrity enforced by architecture. Fixes the global-element button problem.▶
WP problem: Clients editing in Bricks regularly break the site — off-brand decisions, overridden breakpoints. Flip: clients edit content, not structure; brand integrity enforced by architecture.
  • Giving full builder access is a slow erosion of the work we delivered — one session, and the site looks nothing like what was approved.
  • Not about blaming careless editing — the tool gives too much power over structure to someone untrained on it.
  • The flip is architectural, not procedural: content lives in the CMS and is fully editable; layout lives in code and is locked.

Echoes slide 8This is the global-elements problem in a nutshell — in Bricks, a button is often one global element, editable everywhere from one place. In Storyblok, a button is a component instance with its own content fields — editing one can't touch any other button anywhere on the site.
If asked"Won't clients feel restricted?" → "More useful control, not less — full control over every word, image, and button, with zero risk of accidentally breaking the page."
25Performance GTM/HubSpot keep full functionality — they just stop blocking the page. "Blocking" explained literally, then the 3 fixes.▶
WP problem: HubSpot, GTM, tracking scripts slow the site; Lighthouse scores need constant re-optimization. Flip: Astro's island architecture sandboxes scripts; 90+ scores are structural.
  • Every tool marketing adds competes for the same bandwidth at render time.
  • A Lighthouse score on WordPress is a high-water mark, not a baseline — it erodes the moment someone adds a new tag.
  • The flip: third-party scripts load in their own sandboxed "island." HubSpot literally cannot block the rest of the page from rendering.
Real example"GTM alone is almost always the single biggest performance bottleneck on WordPress — deferring it correctly can swing a Lighthouse score 25+ points on its own. In the new stack, that category of problem doesn't exist."
If pushed: "We still need GTM and a bunch of third-party scripts — won't that bring the slowdown back?"

Nothing is being removed. They keep GTM, HubSpot, ad pixels, chat widgets — whatever they want. What changes is how the browser deals with those scripts, not whether they run.

1. What "blocking" literally means: the browser reads HTML top to bottom, building the page as it goes. Hit a script tag not marked to load "later," and it stops everything, fetches the script, runs it fully, then resumes. That's a literal pause, not a metaphor for slow. Google's own default GTM snippet is written to block by default. Analogy: a single-lane road — every script is a car that has to fully pass before the next one, including your page content, can move.

2. The three real fixes:

  • Deferred loading: scripts load after the visible page has already painted, not before.
  • Off-main-thread execution (the big one): GTM/HubSpot run in a separate background lane (a web worker) instead of sharing the page's own processing lane. Still fires every tag — just isn't competing for the same time.
  • Astro Islands (selective loading): only interactive parts ship JS, and each loads independently on its own schedule. A slow widget can only ever block itself.

3. Close the loop: every GTM tag still fires, HubSpot still tracks the same behavior into the same CRM, forms submit the same way, pixels attribute the same conversions. Only the order of operations and processing lane change.

If asked"What about a pixel that needs to fire immediately for ad attribution?" → "Most pixels need to fire before the visitor leaves, not before the page paints — the difference is milliseconds. If something genuinely needs to fire first, we make that one deliberate exception instead of defaulting every script to block."
26Stack Complexity No caching plugins needed — the site is never the slow version underneath. NitroPack/WP Rocket's CSS-breaking bugs are the cautionary tale.▶
WP problem: Paid plugins required on every build; hours of engineering just to reach a starting point. Flip: two tools replace many; zero engineering overhead before client work begins.
  • Before a developer touches anything client-facing, there's setup work that exists only to compensate for WordPress's defaults — invisible to the client, billed as hours or eroded margin.
  • The flip: Storyblok and Netlify replace a half-dozen specialized tools and handle deferred loading, caching, and CDN delivery by default.
If asked: "Doesn't dropping caching plugins introduce risk?"

How WP/WP Engine caching actually works: WordPress builds every page fresh, live, per visitor — slow at volume, so a cache layer saves a pre-built snapshot instead. WP Engine provides one layer server-side; we've added a second with plugins like NitroPack and WP Rocket.

The problem: stacking layers gets fragile. Real, repeated issues with both — including sitewide CSS-breaking bugs from their file-optimization features (minifying/combining CSS), severe enough that full disablement was sometimes the only fix. Also stale snapshots showing old content, and JS-delay features breaking sliders/forms/animations tied to load order.

The recurring support pattern: "clear your cache" is almost always step one when something looks broken or out of date — sometimes at three levels before it resolves. Confusing for a client to hear "your edit is correct, you're just looking at an old copy."

Why Astro doesn't have this problem: the site is built into plain HTML files once, ahead of time — not per visitor, not through a plugin layered on a slower system underneath. The fast version is the only version. Storyblok triggers an automatic rebuild on publish; Netlify deploys it; there's no second cache layer to fall out of sync, so "clear your cache" stops being a step anyone needs.

"No loading hacks" — what that specifically means

On WordPress, deferred/optimized script loading is handled by the same plugin layer doing the caching — NitroPack/WP Rocket's "delay JavaScript execution" features are exactly where we've seen the most breakage, firing scripts out of the order a page needs them in.

In Astro, deferred/isolated loading isn't a plugin feature bolted on — it's how the framework already works, set directly in the page's own code, version-controlled in GitHub. Nothing fragile to re-verify after a plugin update, because there's no plugin layer to break it.

If asked"Is two tools really enough to replace all of that?" → "Storyblok handles image optimization, SEO metadata, scheduling, and CDN delivery natively. Netlify handles deployment and performance. Together they cover what used to take five separate paid plugins plus manual engineering."

  • Templates get you maybe 60% of the way; the remaining 40% — builder config, field setup, breakpoint testing — is still manual and billable.

Echoes slide 8This is exactly what solves the mid-build comparison-page problem — a client wanting "us vs. competitor" pages never in the original sitemap normally means a from-scratch build. 28Security & Maintenance No plugins, no attack surface. Cwicly's shutdown and the WP Engine/Automattic dispute are the two vendor-risk stories here.▶
WP problem: Plugin updates have taken entire sites offline — white screen mid-campaign, no instant recovery. Flip: static HTML has no PHP runtime, no database, nothing to patch.
  • This isn't hypothetical — every WordPress agency has a war story, and we have several.
  • The irony: the security work itself is what causes the outages. Every patch is a small gamble against your other plugins.
  • Monthly security patching isn't a service — it's a tax for the privilege of not getting hacked.
  • The flip: static HTML has no attack surface. "No plugins" sounds like a limitation — it's actually the point.
Real example"We've seen plugin combinations break a site in ways that take hours to trace — a theme self-hosting fonts outside WordPress's pipeline can quietly defeat a caching plugin, and nothing in the logs tells you why."
Echoes slides 8 & 26NitroPack and WP Rocket, brought in to help performance, have caused sitewide CSS-breaking bugs — sometimes requiring full disablement. The tool installed to make the site better became the thing that took it down, sitewide, all at once.
Echoes slide 8The staging-skip pattern — clients editing the live site directly instead of staging, even after a full walkthrough, so the safety net never gets used. The new system has no separate "staging discipline" to remember — every change goes through a build-and-preview step before going live.
A different flavor of risk — losing the tool itself

We were midway through a client build on the Cwicly page builder when Cwicly announced it was discontinuing the product entirely — not a bug, the tool going away. Everything already built was stored in Cwicly's own proprietary format, unreadable by anything else — a full rebuild in Bricks followed. Only the idea of the design transferred, not the build.

Why this can't happen the same way now: a page builder stores layout as proprietary data inside the WordPress database, meaningful only to that one tool. In the new stack, page structure is just code — Astro components in a GitHub repo both Primer and Lock 8 can access, in a standard, open format. If any tool ever went away, it's a rewiring job (reconnect content, redeploy host), not a from-scratch rebuild.

A live, ongoing example of platform-level risk

WP Engine and Automattic (the company behind WordPress.org, run by WordPress co-founder Matt Mullenweg) have been in an active legal dispute since late 2024 over trademark use and contribution to the open-source project. At one point, Automattic blocked WP Engine-hosted sites from automatically updating plugins/themes through WordPress.org's official system — affecting hundreds of thousands of sites through no fault of their own. A court ordered access restored; the lawsuit is still active as of mid-2026, with trial not expected until 2027.

Why it matters here: it's a risk that has nothing to do with code quality — a single entity controlling critical infrastructure for an entire ecosystem, with power to cut off access over a business dispute. That sits above anything Primer or Lock 8 can control on a WordPress site.

Keep neutral if mentioned — still being litigated, both sides dispute the other's claims. The point isn't who's right, it's that this single-point-of-control risk doesn't exist in a stack where hosting, CMS, and codebase are all independently swappable.

If asked"What about backups/recovery time?" → "Recovery on WordPress still means restoring a database and re-testing plugin compatibility — not instant. On a static site, a bad deploy is one click to roll back. There's no database state to restore."

Appendix — How Day-to-Day Actually Works

iStaging vs. live in the new system No separate URL to remember — content edits have a built-in draft/publish state, and code changes get an automatic preview link.▶

Right now on WP Engine, a client gets a staging copy, makes changes there, then someone pushes those changes live once approved — and the whole thing depends on people remembering to use it, which doesn't always happen (slide 8).

The new system splits this into two layers, neither dependent on a client remembering a separate URL:

  • Content edits (almost everything a client touches) — Storyblok has a built-in draft and publish state. A client edits a page, previews exactly how it'll look, and nothing changes on the real site until they hit Publish. The draft is the staging environment.
  • Structural/code changes (Primer's work, not the client's) — every change goes through GitHub, and Netlify automatically spins up a temporary preview link before anything merges into the live site. Automatic, not something anyone has to remember to use.

Net effect: clients get a simpler, built-in version of what staging was supposed to do, and the riskier layer is locked into a review process they don't operate themselves.

iiCreating posts & managing a resource library Fill out a form and publish — same feel as WordPress, minus the ability to break the layout doing it.▶
  • A "Resource" (or "Post") content type gets set up once during the build — title, summary, body, featured image, category, publish date, all defined up front.
  • After that, adding a post is just filling out a form: click "New Story" inside the Resources folder in Storyblok, fill in the fields, publish — or save as a draft to review first.
  • The listing page that shows all resources updates on its own, pulling live from Storyblok — a newly published post just shows up, no extra step to add it anywhere.
  • The practical feel is close to WordPress's Posts screen. The difference: there's no layout to accidentally mess up while doing it.
iiiMigrating content from WordPress to Storyblok A one-time migration Primer handles as part of the build — not an ongoing client task.▶
  • Existing content (blog posts, resource pages, etc.) gets pulled from WordPress via its REST API or a direct export, then mapped into Storyblok using Storyblok's own import tooling — a WordPress post becomes a matching Storyblok story with the same title, body, and images.
  • Images and other media move into Storyblok's asset library as part of the same process; internal links get updated to match the new site's URLs.
  • This happens as part of the build itself — the "Content Migration" stage in the Flow diagram on slide 31 — not a manual task for Lock 8.
If asked"Do we lose anything in the move?" → "No — anything migrated maps over directly. What doesn't carry over is anything that depended on a specific WordPress plugin's or builder's particular quirks to display correctly — the same brand-drift protection slide 24 already covers."

The Stack (slide 23)

Astro — The framework the new website runs on. Builds pages ahead of time into fast, lightweight files instead of assembling them fresh for every visitor like WordPress does.
Storyblok — The headless CMS — the actual screen Lock 8's team logs into to edit content, swap images, update CTAs. Direct replacement for editing inside WordPress/Bricks.
Claude Code — Anthropic's AI coding assistant. Helps write, review, and document code faster — doesn't make creative or brand decisions, every line reviewed by a human before it ships.
Netlify — The hosting platform. Serves the built site to visitors worldwide, auto-redeploys when something changes.
GitHub — Where the site's code lives and is version-controlled — every change ever made is tracked.
Figma — The design tool already in use; unchanged, just now feeds directly into the build pipeline.

Architecture & how the build works (slides 22, 25, 26, 28, 31–34)

Headless CMS — Content (words, images, buttons) stored separately from how it's displayed. "Headless" means no built-in front-end — content gets pulled into whatever renders it (Astro). This is why clients can edit content but can't break layout.
Static site / static HTML — A site pre-built into plain files ahead of time, not assembled live per visit like WordPress. No database, no server-side code per visit — faster, nothing for a hacker to exploit.
Webhook / automatic rebuild — A notification one system sends another the instant something happens. Storyblok sends a webhook to Netlify on publish, triggering an automatic rebuild — no manual cache refresh needed. Why there's no "stale cache" problem.
Island architecture — Astro isolates interactive elements (a form, a widget, a tracking script) into independent "islands" that load on their own. One slow/broken island can't hold up the rest of the page.
CDN (Content Delivery Network) — A worldwide network of servers caching copies of the site so visitors load from a nearby server. Faster everywhere, included with Netlify hosting.
Design tokens / "tokens.css" — Brand colors/fonts/spacing in one reusable file every component reads from. Update the file, the whole site updates consistently.
Component library — Pre-built, reusable building blocks (buttons, headers, cards) pages assemble from instead of custom layouts from scratch. The engine behind Delivery Speed (slide 27).
Plugin (WordPress context) — An add-on for a feature (forms, SEO, page building). Also the most common source of conflicts and security holes, built by many unrelated third parties.
Main thread / render-blocking — The single processing lane a browser uses to build a page. A script is "render-blocking" when the browser must stop building the page to fully run it first — a literal pause, not a metaphor.
Web worker / off-main-thread execution — A separate background lane scripts can run in, away from the page-building lane. GTM/HubSpot can run here — still fully execute, just stop competing for processing time.If asked for the tool name: Partytown is the common library for this — runs third-party scripts in a web worker without changing how those scripts work.

SEO & marketing acronyms (slides 9, 19, 20)

SEO (Search Engine Optimization) — Making a site easier for search engines to find, understand, and rank well.
AEO (Answer Engine Optimization) — Optimizing content so AI answer tools (ChatGPT, Perplexity, AI Overviews) are more likely to pull from it as a direct answer.
GEO (Generative Engine Optimization) — Structuring content so generative AI is more likely to reference or recommend the brand by name within a longer answer.If asked the difference: "AEO is about getting picked as the direct answer. GEO is about getting mentioned and recommended within a longer AI-generated response."
a11y (Accessibility) — Shorthand for "accessibility" (11 letters between the first/last letter). Making a site usable by people with disabilities — screen readers, keyboard navigation, color contrast. Often a legal requirement.
Lighthouse score — Google's automated grading tool for a webpage's performance, accessibility, and SEO health, 0–100.
Page speed — How fast a page loads for a visitor — a major factor in both UX and SEO/AEO ranking.
